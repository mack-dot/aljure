# Minimal autonomous executable-learning development check — v1

Approval pending. This replaces the proposed 54-task development run for the
next inference request. It does not amend old plans or results. No model call
may start without explicit approval of the new plan hash.

## Scope and data

Run one ES trajectory with six new synthetic development tasks, generated by
`benchmark.learning_development`, seed 20261102. The fixed order is:

1. Route 64 records; count `hold`.
2. Route 72 new records; count `expedite`.
3. After a cold restart, route 80 new records; count `retry`.
4. Route 88 new records; count `hold`.
5. Route 96 new records; count `expedite`.
6. Classify 24 parity records; count `even`. This is an incompatible-task control.

Routing uses a declared priority rule over blocked status, age, and attempt
count. The model receives the rule and one task at a time. It receives no
classifier code, named skill invocation, gold labels, or worked solution.
The controller-only validation panel has 36 other routing records and 12 other
parity records. Every task and panel has disjoint record texts and disjoint
feature tuples even after identifiers are removed. Preparation and preflight
verify this property and the exact deterministic generator output.

“Unseen” means absent from earlier tasks and the validation panel in this live
trajectory. These are newly generated development tasks. The task generator and
rules are known during implementation. This is not held-out evaluation, a
contamination claim, a comparison, or evidence of broad generalization.
No historical task corpus, held-out task, or external dataset is read.

## Mechanism and isolation

Use existing structured ES acquisition, Sonnet 5.5, medium adaptive thinking,
and subscription transport only. No API fallback, seeded artifact, auto-capture,
controller repair of proposals, model switch, or second prompt variant.

Start with an empty library. Offer the existing proposal/decline turn only
after tasks 1 and 2. Charge both calls. Validate each submitted candidate with
the existing v2 rule: at least 95% precision and 10% coverage on admitted panel
records, no execution/type error, no loss of a previously correct record,
nondecreasing library coverage, and at least one additional correct record.
Disable label-abstention adaptation. Preserve declines and rejection reasons.

Exit after task 2. Resume in a different runner process with a new JVM, worker,
and conversation. The runner rejects resume in the same process. Carry only
the verified library and evidence ledger. Tasks 3–6 use that frozen library;
they cannot propose or promote. No outcome feedback changes a skill or prompt.
Each task sees only its public input and admitted artifact interface/code.
Controller answers and validation records stay outside the model and worker
task inputs. Workers have no filesystem or network capability.

## Acceptance criteria

A GO requires all six tasks attempted, complete provider accounting and safety
evidence, and all of the following:

- A model-authored proposal is validated and committed before restart.
- Its library pin remains unchanged for all four post-restart tasks.
- On each of tasks 3, 4, and 5, the model chooses a call to a pre-restart code
  hash, the call returns at least one valid routing label, and the final answer
  is exactly correct. Nil-only returns do not qualify.
- Task 6 has a correct answer, records an applicability refusal, and does not
  invoke a pre-restart skill.

Preloading does not count as reuse. Scripted requests do not count as autonomy.
A successful return alone does not prove a correct answer. This is a single
development demonstration; it cannot establish an accuracy or cost advantage.
All six completed with a missed criterion is NO-GO. Interrupted or unaccounted
execution is INCOMPLETE. Do not rerun selected tasks or change thresholds.

## Limits and reporting

Hard aggregate cap: **$3 API-rate-equivalent**. Per task: **$0.50**, 12 model
calls including acquisition and children, 300 task seconds, and the frozen
token/output limits. Before each task, known spend plus unknown reservations
plus the full $0.50 task cap must fit within $3. Validation has a separate
600-second bound and makes no model calls. Actual subscription billing and
local compute dollar cost are unknown; report validation/runtime seconds.

Run serially. Check at least 6 GiB free disk before each task. Stop on provider
uncertainty, isolation/cleanup failure, Docker restart, integrity failure, or
promotion crash/fatal error. Keep the prior pin, receipts, answer rows, orphan
files and reservations. A crash cannot resume as a cold restart. Credential
refresh and API fallback are not authorized.

Report all six task outcomes, exact accuracy, mean score, total known cost and
unknown reservations, cost per successful task, proposal and validation cost,
latency p50/p95, tool reliability, proposal/promotion yield, actual code-hash
calls/returns, and post-restart successful reuse tasks per acquisition dollar.
Zero denominators are undefined/infinite, never zero. Keep all failures.
